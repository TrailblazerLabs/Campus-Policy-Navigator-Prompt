# Review: Campus Policy Navigator Prompt

> **Status:** AI reviewed version 1.0.0 of the prompt prior to its release as an open source solution. Every finding below was addressed in version 2.0.0; see `../CHANGELOG.md`. It is kept here as the rationale record for why the prompt is shaped the way it is, so future editors can see what problem each piece of structure solves before removing it.

## Bottom line

The instruction logic in this prompt is unusually disciplined for an LLM prompt: it separates evidence classes cleanly, refuses to let the model infer completion or resolution from unverified text, and builds in real guardrails against prompt injection from retrieved content. That part does not need a rewrite, it needs protection from the platform constraints below.

The most serious problem is not wording, it is fit: as written, this cannot be deployed as a single Flex prompt template in Prompt Builder. It also asks one LLM call to do work that Salesforce's own data model can do more reliably. Those two issues, plus a handful of smaller gaps, are covered below in priority order.

## 1. This exceeds the Flex template input limit (blocking)

Prompt Builder caps a Flex template at five inputs total. Counting the merge fields declared in the Inputs section, this template defines thirteen: Institution_Name, Current_Date_Time, Requested_As_Of_Date, User_Query, Audience_Type, Authorized_User_Context, the Get_Applicable_Policy_Source_Bundle flow output, Confirmed_Policy_Evaluation_Results, Confirmed_Action_Results, Source_Governance_Configuration, Source_Quality_Warnings, Approved_Service_Directory, and Include_Internal_Trace. Whoever tries to build this in Prompt Builder will hit the limit immediately, not as a style problem but as a save-blocking validation error.

The fix does not require cutting any of this information, it requires consolidating how it arrives. Have the orchestrating flow (the one already producing Get_Applicable_Policy_Source_Bundle) assemble a single structured context object that bundles the source bundle, the confirmed evaluation results, confirmed action results, source governance configuration, source quality warnings, and the service directory into one flow output. That collapses six inputs into one. Institution_Name, Current_Date_Time, Requested_As_Of_Date, Audience_Type, and Include_Internal_Trace can similarly be folded into a single "session context" input rather than five separate ones. That leaves realistically two or three top-level inputs (User_Query, Authorized_User_Context, and the consolidated context object), comfortably under the limit, with no loss of the information the instructions depend on.

## 2. Push deterministic filtering into the flow, not the model

The CURRENT POLICY AND REGULATION VALIDATION section asks the model to check active status, effective-date ranges, and version-to-clause linkage across three parallel object families (external regulation, institutional policy, regulatory code) before it can use a source. This is exactly the kind of multi-table join and date-range filter that a flow or Apex query does deterministically and an LLM does probabilistically. Asking the model to re-derive "is this the one active, in-effect, correctly-linked clause" from a bundle of raw records is where hallucinated citations and wrong effective dates are most likely to creep in, and it is also the hardest failure mode to catch in testing because it will look right most of the time.

The more reliable design has Get_Applicable_Policy_Source_Bundle (or a dedicated Apex/query action) do that filtering before the bundle ever reaches the model: return only the version and clause that are already active as of the resolved as-of date, with overlaps and conflicts already flagged as data rather than left for the model to discover by re-reading five eligibility conditions three separate times. The model's job then shifts from "audit these records for validity" to "explain this pre-validated result and cite it," which is both safer and cheaper per call. The same logic applies to AcadTermEnrlPolicyRuleLog matching (Published vs Calculated, matching six identifiers) and to registration-timeline selection: keep the natural-language description of what "published and applicable" means as a comment for whoever builds the flow, but do not rely on the model to execute it correctly on every call.

If a full rebuild of the grounding flow is not feasible right now, at minimum keep the current instructions (they are already correctly strict) and treat this as a roadmap item, since it is the difference between "usually right" and "reliably right" at scale.

## 3. Audience_Type is declared but never used

The Inputs section defines `<audience_type>`, but no instruction in the body references it. Either wire it into the prompt (for example, adjust vocabulary and formality for prospect/applicant vs. faculty/staff audiences, since a prospective student and a department chair need different levels of institutional jargon) or remove it from the inputs. An unused input is a small thing on its own, but it is exactly the kind of gap that is easy to miss in a document this long and worth catching before it goes live.

## 4. Harden the action rules against the known Agentforce prompt-injection pattern

Security researchers have already demonstrated a real attack against Agentforce agents in which instructions embedded in ordinary CRM data (a lead form submission) were treated as legitimate commands once an internal user asked the agent to review that record, leading to bulk data exfiltration. This prompt already has the right instinct: it tells the model not to follow instructions embedded in policy descriptions or clause text. Given that this agent can also take consequential actions (register, withdraw, appeal, waive, resolve, remove), it is worth extending that same rule explicitly to the ACTION RULES section: an action should only be triggered by the current authenticated user's own request in User_Query, never because retrieved content (a clause description, a violation note, a prior case comment) contains text that reads like an instruction. This is one sentence to add, and it closes the exact gap that was exploited in the published attack.

Separately, since the prompt itself cannot enforce permissions, flag to your Salesforce team that the actions this agent can invoke should be scoped with least-privilege permission sets and that any outbound-communication action (confirmation emails, notifications) should be restricted at the action/flow level, not left to the prompt to gate.

## 5. Clarify how Audience_Type relates to Authorized_User_Context for access decisions

The Privacy and Access section distinguishes "unauthenticated" from "authenticated" users but never states which input establishes that: Authorized_User_Context or Audience_Type. If Audience_Type can be set by a front-end channel independent of real authentication, a malicious or misconfigured caller could pass Audience_Type = Staff without actual authorization. Add one explicit sentence: access-level and disclosure decisions are always derived from Authorized_User_Context; Audience_Type affects tone and framing only, never what information is disclosed.

## 6. Consolidate the three near-identical validation checklists

Sections A (external regulations), B (institutional policies), and the RegulatoryCode validation block each repeat a nearly identical five-point active/effective/linked/matched checklist with only the object names swapped. Beyond the length this adds, having three parallel copies of the same rule is a maintenance risk: a future edit to one (say, adding a sixth condition) is easy to make in one copy and forget in the other two, and the model may apply them slightly inconsistently since they are not framed as literally the same rule. Consider stating the test once as a named rule ("the Active-and-Applicable Test") and then referencing it by name for each evidence class, calling out only what differs (which object pairs, which extra applicability fields). This shortens the template and reduces the chance of drift.

## 7. "Approved" is overloaded

The word "approved" is used for at least six different things across the document: an approved action, an approved human contact, an approved external link, an approved confirmation number, an approved alternative path, and an approved policy version's governance status. Each of these is gated by a different source (Source_Governance_Configuration, Approved_Service_Directory, or a Confirmed_Action_Results flag), but the prompt never says so explicitly at each point, so the model has to infer which "approved" it means from context. A brief terminology note near the top ("approved" always means explicitly authorized by the governing source named in that section) plus tightening a few instances (for example, "public supporting link, when Source Governance Configuration marks it approved for display") would remove that ambiguity.

## 8. Verify the object model against your actual org schema

RegulatoryAuthority, Regulation, RegulatoryCode, and RegulatoryCodeViolation are standard objects from Salesforce Public Sector Solutions, not Education Cloud. CompliancePolicy, CompliancePolicyVersion, CompliancePlcyClauseVersion, AcademicTermPolicyRule, AcadTermEnrlPolicyRuleLog, and AcademicTermRegstrnTimeline read as custom objects built for this institution (the truncated API-name style is typical of the 40-character object name limit). That combination is workable, but it means two different provisioning questions before this goes further: confirm Public Sector Solutions is actually licensed and installed in this org for the regulatory-code objects to exist, and confirm the exact field names referenced in the prompt (IsActive, CanResolveAutomatically, and the various Status/effective-date fields) match your schema rather than a close approximation, since the model will treat these as literal field names when it reasons about the bundle.

## 9. Add a small number of worked examples

Salesforce's own guidance on writing Agentforce instructions emphasizes giving the model positive examples rather than instructions alone, and iterating with Plan Tracer. This prompt has zero worked examples for a task with at least five materially different response shapes: a general policy question, a "why do I have this hold" question, a registration-timeline question, a conflicting-sources case, and the two verbatim fallback cases it already defines well. Adding one short example transcript per branch (even abbreviated) would reduce the variance you will otherwise see in testing and gives you concrete acceptance criteria for QA.

## 10. Minor items worth a look

Nothing here blocks deployment, but worth a pass:

The prompt does not say how to treat a follow-up turn that changes the as-of date or scope mid-conversation (for example, "what about for spring 2027?"), which matters once this runs in a multi-turn Agentforce session rather than a single call.

If this agent will ever be used by international students or multilingual staff, the prompt is silent on response language; worth an explicit line either committing to respond in the query's language while keeping citation labels in English, or stating that this is out of scope for now.

Given this serves students directly, consider one explicit line grounding the privacy rules in FERPA (no disclosure of one student's education record to another, ever, regardless of how the request is phrased), since that is the actual regulatory floor this agent operates under and it strengthens the rationale for staff reviewing the prompt later.

## What is already working well

Worth calling out explicitly so nothing here reads as a wholesale rewrite: the refusal to treat user-supplied claims as proof of policy, deadline, completion, or resolution is exactly right and is the single most important guardrail in the document. The verbatim fallback strings reduce variance in exactly the places where consistency matters most. The precedence rules for conflicting active records, and the instruction to route rather than adjudicate when a regulation and policy appear inconsistent, correctly keep the model out of legal-interpretation territory. The citation structure and the internal-trace gating are both well thought through for an audience that spans public-facing and internal users.

## Suggested next step

The Flex-template input limit is the one item that will stop this from being built at all, so it is worth resolving first, ideally by getting your flow team to prototype the consolidated context object described in item 1 before any further wording changes. Everything else here can be layered in afterward without touching the underlying architecture.
